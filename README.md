# 影像片段授权证据与展陈终端发布

这里是可离线启动的合成上游，所有编号、时间和凭据都用于联调。

## 本地运行

使用 Node.js 22.23.4。项目只使用随 Node.js 提供的运行库。

```sh
npm start          # 单独启动合成上游（联调用）
npm run demo       # 进程内跑完整四阶段演练并输出策展报告，落 var/demo-journal.jsonl
npm test           # 单元测试 + 来源核对 + 端到端演练
```

### 策展人命令行

`npm run demo` 生成事件日志后，可用 CLI 查询（`--json` 输出机器可读结果，`--journal` 指定其他日志路径）：

```sh
node src/cli.mjs schedule                              # 展期安排：片段、许可依据、终端、人工联系点
node src/cli.mjs contacts                              # 只看待人工联系的点位
node src/cli.mjs playback P2 feature --at 2026-12-05T10:30:00+08:00
```

不同终端分别启动服务和执行独立来源测试。默认地址为 `http://127.0.0.1:4173`，可通过 `SOURCE_PORT` 设置端口，也接受通用的 `PORT`，同时设置时以 `SOURCE_PORT` 为准。`GET /health` 用于确认来源服务已就绪。来源使用进程内演练时钟，启动时处于 `booking`。用 `PUT /_source_clock?step=restrict` 推进到下一阶段，`GET /_source_calls` 查看本实例收到的业务请求。可查阶段为 `booking`、`restrict`、`late`、`restore`。重启服务会重置时钟和请求记录。预置的源端回执按演练阶段出现，和本地应用是否已处理某次回执是两回事。
`npm test` 核对可访问的上游响应和合成资料。

## 来源约定

编目页面的 `data-edition` 是成片版号，`data-part` 是被引用素材，`data-in`、`data-out` 为引用素材上以秒计的半开区间。`/catalog/links` 给出派生素材的区段对照，`at` 是派生开始点，对应原始素材上的同长度区段，不跨增速或倒放。`/exhibits/schedule` 的 `screen` 与 `slot` 指向一个编目位。
`/rights/entries` 包含随业务时间推进收到的许可修订，撤回即按其 `effective` 为所指许可缩短生效范围。授权只覆盖同一介质、用途及地点；`/rights/amendments` 返回涉及限定条款的正文。`/player/commands` 接受含 `screen, slot, sequence, action, edition` 的 JSON；`/player/receipts` 用相同身份回传收件、应用或失联。命令入口的响应仅表示请求到达，应用以设备回执为准。

## 应用层（`src/`）

| 模块 | 职责 |
| --- | --- |
| `catalog.mjs` | 解析编目 HTML，按 `/catalog/links` 把派生素材**递归还原**到原始素材区段，画面与声音分开 |
| `time.mjs` | 带时区的半开区间 `[start,end)`、时间轴切分、相邻整数区段合并与缺口计算 |
| `rights.mjs` | 把授权条目与修订（撤回/收窄/恢复）折叠成时间轴上的有效片段，按原始区段逐段取证 |
| `distribution.mjs` | 终端账本：同一 `(screen,slot)` 只接受严格递增且连续的发布序号，管理待确认/已确认状态 |
| `journal.mjs` | 追加式事件日志（判断、命令、到达、回执），支持重放重建 |
| `orchestrator.mjs` | 每个同步周期重新采集并重新判断，决定上线/下线/冻结/切换替代成片 |
| `views.mjs` / `render.mjs` | 策展总览与“按一次放映回看”的对象模型及中文报告 |
| `cli.mjs` / `demo.mjs` | 命令行入口与四阶段端到端演练 |

### 判定与发布规则

- **以原始区段为准**：成片间接引用另一版素材时，先展开到原始素材坐标再核对授权；同一素材相邻有效区段允许共同覆盖。
- **音画分别取证**：声音和画面各需独立授权证据，单一已授权来源不能放行混合版本；授权只在同一介质、用途、地点内有效。
- **三种结论**：`cleared`（依据完整）、`blocked`（硬缺口，须撤下）、`frozen`（来源断档或限定条款无法解释，只冻结受影响安排，并指出缺的是哪类使用许可）。硬缺口优先于冻结。
- **重新判断而非状态残留**：每个周期都重新拉取全部资料；恢复授权后自动重算。撤回在终端确认下线前，策展视图持续提示“仍可能播出”，掉线的 `offline` 回执不能用本地“已发出”冒充停止。
- **序号与迟到回执**：旧序号/跳号命令一律拒绝；迟到的上线回执若已被后续命令超过，仅留痕并标记 `superseded-sequence`，不能复活已撤回版本。
- **替代成片**：可先预备；只有使用范围完整（`cleared`）且收到终端上线确认后，对应编目位才记为已更新。
- **可回看**：事件日志只追加不改写，保留送出了什么、为何撤回、终端何时确认；`playback` 按时点还原当时实际在播版本（可能不同于展期安排版本）及其授权依据。

### 四阶段演练故事线

1. `booking`：馆内 P1 与网页 P2 对 `cut1` 的音画授权均完整，分别下发序号 1 上线。
2. `restrict`：网页照片授权 `web2` 被撤回、`web0` 被收窄到馆内，网页 `cut1` 出现硬缺口 → 下发序号 2 下线；馆内授权不受影响继续放映。此时仅收到 `offline`，P2 列入人工联系。
3. `late`：序号 1 的上线回执迟到，被标记忽略；序号 2 下线 `applied` 后状态才转为停止。
4. `restore`：`web0` 恢复但 `web2` 仍撤回，`cut1` 不可恢复；不含照片素材的替代版 `cut2` 授权完整，下发序号 3 上线，终端确认后编目位才标记更新。
